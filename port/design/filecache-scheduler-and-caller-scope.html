FileCache 后台调度：BackgroundSchedulePool 迁移设计

这份文档说明 ClickHouse BackgroundSchedulePool 的调度算法，以及 Velox FileCacheScheduler 的迁移算法。正文以 FileCache 的两个真实后台 task 为例，逐个场景对比“CH 得到的算法”和“我们的迁移算法”；附录按三个类分组给出函数与 成员变量的精确映射。

先说结论

目标不是重新设计一个通用后台调度器。 目标是保留 FileCache 实际依赖的调度合同，把底层线程与定时机制换成 Velox 的 folly::Timekeeper 加 FileCacheWorkerPool。

允许改变：定时器实现（CH 集中式 delayed_thread 加 multimap → 每任务一个 folly::Future）、执行线程来源、命名、去掉 StorageID 与 task grouping、去掉 ZooKeeper watch callback、去掉 activate 复活语义。

不允许改变：任务状态机、schedule 的幂等合并、immediate 请求压过 delayed 请求、deactivate 等待运行中回调结束、holder 析构即安全停任务。

1. 为什么需要它

大白话：ClickHouse 里有海量“偶尔要跑一下、跑完就睡”的周期性小杂活——每张 ReplicatedMergeTree 表的队列拉取、mutation 检查、临时目录清理……如果一件活配 一个专职线程，一个集群几万张表就是几十万个基本在睡觉的线程，内存和调度全部爆炸。

BackgroundSchedulePool 的解法是一个共享的小工人班组，加一堆任务卡： 活不占线程，只占一个任务对象；真要跑的一瞬间才借一个 worker。它给出的核心保证写在头注释里：

同一个任务永远不会被多个 worker 同时执行。不同任务之间可以并行。

FileCache 复用同一套设施来跑它自己的后台维护工作。Velox 侧没有 BackgroundSchedulePool，所以 FileCacheScheduler 把这套语义搬到 folly::Timekeeper（定时）加 FileCacheWorkerPool（执行）之上。

2. 三个类，以及 FileCache 注册的两个 task

FileCache::initialize 里注册了两个 task，正文全程用它们举例：

background_cleanup_task

FileCache.cpp:559-563。单一维护任务：清理失效条目 + 空闲客户端驱逐。 既被事件驱动（失效通知），又周期驱动（定时），是本文的黄金例子。

keep_up_free_space_ratio_task

FileCache.cpp:591-592。维持磁盘 free-space 比例，回调末尾自我 scheduleAfter 形成纯周期心跳。仅在配置了 ratio 时注册。

两个 task 都通过 getSchedulePool().createTask(...) 登记，返回的 holder 存成 FileCache 成员。登记不等于派工——下面第一个场景就讲这点。

场景一：登记，但先不跑

FileCache 初始化时创建 background_cleanup_task，随即打上第一次延迟； 如果初始化失败，要能安全撤掉： 

background_cleanup_task = ...getSchedulePool().createTask(
    StorageID::createEmpty(), "FileCacheBackgroundCleanup",
    [this] { backgroundCleanupTaskFunc(); });          // 登记：只填卡
main_priority->setInvalidateNotifier(threshold,
    [this] { background_cleanup_task->schedule(); });   // 事件驱动的钩子
background_cleanup_task->scheduleAfter(backgroundCleanupIntervalMs());  // 第一次延迟派工
// 失败路径： if (background_cleanup_task) background_cleanup_task->deactivate();

CH 算法createTask

createTask（BackgroundSchedulePool.cpp:447）只做 new TaskInfo(fn)。此刻四个标记全 false：

scheduled = false
delayed   = false
executing = false
deactivated = false

任务不在任何队列里，只是“存在”。随后 scheduleAfter 才把它交给 delayed_thread 排期。

迁移算法createTask

FileCacheScheduler::createTask new FileCacheScheduledTask， 初始 state_ = Idle；holder 持有唯一的 shared_ptr<FileCacheScheduledTask>。

state_ = Idle
generation_ = 0
callbackInFlight_ = false

scheduleAfter → armTimerLocked 挂上 timekeeper_->after(delayMs)，句柄存进 timerFuture_， state_ = Delayed。

定时架构差异：CH 用一个进程级 delayed_thread + 按到期时间排序的 multimap<Timestamp, TaskInfoPtr> delayed_tasks 集中管理所有延迟任务；port 每个任务自带一个 folly::Future timerFuture_。公开语义相同，内部实现不同。

场景二：失效通知来了，要立刻清（事件驱动）

当失效条目攒够阈值，priority 层通过 setInvalidateNotifier 注册的回调直接调 background_cleanup_task->schedule()。一次抖动可能触发很多次——必须合并成一次。

CH 算法schedule

schedule():                       // .cpp:47
  if (deactivated || scheduled) return false   // 已排 → 合并掉
  scheduled = true                             // scheduleImpl, .cpp:221
  if (!executing) pool.scheduleTask(*this)     // 未执行 → 立即入队
  if (delayed)    pool.cancelDelayedTask(*this)// 撤掉待跑的延迟

scheduled 是粘性 bool：多次 schedule 只产生 一次待执行。delayed 被取消 —— immediate 抢占 delayed。

迁移算法schedule

schedule():
  if (state_ == Deactivated) return false
  if (Idle || Delayed):
    cancelTimerLocked()          // 撤 timer, generation_++
    queueImmediateLocked()       // state_ = Queued, 入 workerPool_
  if (Queued) return false       // 合并
  if (Running): pendingImmediate_ = true; pendingDelayed_ = false

Queued 状态本身就是 CH scheduled=true 的等价；重复 schedule 撞上 Queued 返回 false，实现同样的合并。

注意 worker 闭包捕获的是 weak_ptr 加一个 generation_ 快照，执行前 重新校验，避免 stale 派发——这一点在场景五展开。

场景三：回调自我重排 —— 满批立刻，没满批延迟

backgroundCleanupTaskFunc 收尾（FileCache.cpp:1954-1957）根据这一轮 清了多少来决定下次什么时候再跑： 

if (removed == invalidated_entries_cleanup_remove_batch)
    background_cleanup_task->schedule();                        // 满批：可能还有，立刻续
else
    background_cleanup_task->scheduleAfter(backgroundCleanupIntervalMs());  // 没满批：例行间隔

关键点：这两个调用发生在回调正在执行的当口（任务处于运行态）。

CH 算法execute 收尾

进入 execute（.cpp:117）时 executing=true, scheduled=false。 回调内的 schedule() 因 executing 只置 scheduled=true，不立即入队。收尾统一处理（.cpp:202-218）：

executing = false
if (scheduled) pool.scheduleTask(*this)  // 末尾才重排
else           return                    // 回到空闲

注释点明：不在这里直接再跑一遍，是为了“让所有任务都有机会执行”，避免自我高频重排饿死别人。

迁移算法runCallback 收尾

runCallback 里 state_ = Running；回调内的 schedule/scheduleAfter 只攒标记，不立即动作。 回调返回后按优先级结算：

if (pendingImmediate_) queueImmediateLocked()   // → Queued
elif (pendingDelayed_) armTimerLocked(delay)    // → Delayed
else                   state_ = Idle

pendingImmediate_/pendingDelayed_ 就是 CH “执行期间被 schedule” 攒下来的意图，只是 port 把它拆成两个具名标记。

场景四：清理途中失效通知又插进来 —— immediate 必须压过 delayed

这是整个迁移里最容易出错、也是 Task 006 corrective（b3c2832e1）修复的地方。真实并发： cleanup 回调正在跑，它自己没满批、打算 scheduleAfter 例行续；与此同时外部失效 通知打进来要 schedule 立刻清。谁赢？

回调运行中
先 schedule()（失效通知）→ 记下“立刻续”；随后回调收尾 scheduleAfter()（例行）。例行不能把“立刻”改成“等一会”。

CH 算法scheduleAfter 的守卫

scheduleAfter(ms, ...):           // .cpp:57
  if (deactivated || scheduled) return false   // ← 关键
  if (delayed && !overwrite)    return false
  if (!delayed && only_if_scheduled) return false
  pool.scheduleDelayedTask(*this, ms)

只要 immediate 已把 scheduled 置位，scheduleAfter 直接返回 false、不记录任何延迟。反向地，schedule 会 cancel 掉一个已排的 delayed。immediate 绝对优先。

迁移算法Running 分支守卫

scheduleAfter(delayMs):
  if (Deactivated) return false
  if (Idle || Delayed): cancelTimerLocked(); armTimerLocked(); return true
  if (Queued) return false
  // state_ == Running:
  if (pendingImmediate_) return false          // ← corrective 加的守卫
  pendingDelayed_ = true; pendingImmediate_ = false; pendingDelayMs_ = delayMs

schedule 的 Running 分支做对称的反向操作 （pendingImmediate_=true; pendingDelayed_=false），一起重现 CH 的 immediate 优先。

corrective 之前的 bug：旧 port 的 scheduleAfter 在 Running 分支 无条件 pendingDelayed_=true; pendingImmediate_=false，即“谁最后调谁赢”。于是例行 scheduleAfter 反而把已排的“立刻续”降级成延迟——缓存明明还有一整批要清，系统却傻等 一个间隔。b3c2832e1 加上 if (pendingImmediate_) return false 修复。

场景五：cache 关闭或初始化失败 —— 安全停任务

初始化 catch 里显式 background_cleanup_task->deactivate()；正常生命结束时， FileCache 析构 → holder 析构 → 自动 deactivate。两条路径都必须：既停掉 未来的回调，又不能打断正在跑的那一次。

CH 算法deactivate 双锁

deactivate():                     // .cpp:76
  lock exec_mutex                 // 拿不到 → 有回调在跑，等它
  lock schedule_mutex
  deactivated = true; scheduled = false
  if (delayed) pool.cancelDelayedTask(*this)

先抢 exec_mutex 天然等待运行中回调结束，再改标记；之后所有 schedule/scheduleAfter 因 deactivated 变 no-op。

迁移算法单锁 + callbackInFlight_

deactivate():
  lock mutex_
  if (Deactivated) return
  cancelTimerLocked()
  wasRunning = (state_ == Running)
  state_ = Deactivated
  if (wasRunning) cv_.wait(lock, [&]{ return !callbackInFlight_; })

port 不用第二把 exec_mutex，而是用 callbackInFlight_ 标记加 cv_ 等待——因为 deactivate 会把 state_ 直接改成 Deactivated，state_ 本身已无法区分“回调跑完没”。

holder 可独立销毁，无需先 drain worker pool：已进 worker 队列的 Queued 闭包、以及 timerFuture_ 上的 Delayed continuation， 都只持 weak_ptr。任务对象被 holder 销毁后，它们 lock() 失败即成为安全 no-op；generation_ 快照失配也会让它们提前 return。所以 FileCache 析构时 两个 holder 各自析构就够，不必先关掉共享的 FileCacheWorkerPool。这是 CH 靠共享 shared_ptr + 关闭前 join 达成的同一个保证，port 用 weak_ptr 达成。

4. 已知遗留（不被这两个 task 触发）

自 deactivate 死锁

若回调同步对自己的 task 调 deactivate，port 会永久等 callbackInFlight_。CH 用 running-thread-id 检查规避，port 缺这一层。 background_cleanup_task、keep_up_free_space_ratio_task 都不自 deactivate，不触发。

tasks_ 无界增长

FileCacheScheduler::tasks_ 里过期的 weak_ptr 只在 shutdown 时清理。FileCache 只注册两个 task，无害。

最终决定

采用 精确公开语义 + 换底层实现：FileCacheScheduler 保留 BackgroundSchedulePool 的状态机、幂等合并、immediate 优先与 deactivate 语义， 底层换成 folly::Timekeeper 加 FileCacheWorkerPool，并用 weak_ptr + generation_ 达成 holder 独立销毁的生命周期安全。 CH 中 FileCache 不用的能力（overwrite / only_if_scheduled / activate / task grouping / watch callback / system-table introspection）不移植。
