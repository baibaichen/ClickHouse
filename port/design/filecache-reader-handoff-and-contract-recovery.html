FileCache remote reader handoff 与 IO compatibility 设计

这份文档是 reader/writer compatibility 的 canonical source of truth。 它保留 Q1/Q2 接力场景、ClickHouse 源码映射、Task 007 偏差分析，以及最终采用的 “公开语义精确、内部 flatten、底层使用 Velox primitive”方案。

先说结论

目标不是重新设计 FileCache reader 协议。 目标是保留 ClickHouse FileCache 实际依赖的 ReadBufferFromFileBase / WriteBufferFromFile 合同， 只把继承结构、内存分配和底层文件 IO 换成适合 Velox 的实现。

允许改变：内部类层级、MemoryPool 分配、ReadFile::pread、 WriteFile::append、Velox exception 类型。

不允许改变：buffer 状态、cursor 结算、next/eof/cancel、 external buffer attach/detach、right bound、reader handoff 和 writer teardown 语义。

1. 为什么需要 remote reader handoff

大白话：多个查询可以接力下载同一个 cache segment。前一个查询下载一个 buffer chunk 后让出 downloader，后一个查询从 cache 当前写入位置继续，并复用同一个 remote reader 的 cursor、连接和可能的预读状态。

查询 Q1
读取 [0, 6)
0123 4567
FileCache
0123 4567
查询 Q2
读取 [2, 8)
23 4567

Q1 已经把 [0, 4) 写入 cache。Q2 先命中 [2, 4)，随后取得 Q1 留在 FileSegment 中的 reader，从 offset 4 继续下载 [4, 8)。

2. 一个 buffer chunk 内发生什么

1

取得 reader

FileSegment 交出 reader。此时：

available == 0
bufferEndOffset == currentWriteOffset
2

借用查询 buffer

reader 临时借用查询拥有的输出 buffer B：

reader.set(B, capacity)
reader.next()
3

同一份 bytes 两用

远端 bytes 直接落在 B，随后：

FileSegment::write(B)
Next returns B
4

先 detach，再 handoff

reader.set(nullptr, 0)
FileSegment owns reader
query still owns B

交接后两边不再互相引用。

核心 ownership invariant： FileCacheInputStream 继续拥有并向上层暴露 B； FileSegment 接管 remote reader；handoff 前 reader 必须完全解除对 B 的引用。

5. 采用的 compatibility 架构

CH FileCache 状态机

按原调用顺序使用 buffer、right bound、seek、handoff 和 writer lifecycle。

→

ch::ReadBufferFromFileBase

只保留 FileCache 实际使用的精确合同；内部 flatten，不移植完整五层通用 IO hierarchy。

→

ReadBufferFromVeloxReadFile

以 ReadFile::pread 实现 nextImpl，owned memory 来自 MemoryPool。

FileSegment::RemoteFileReaderPtr 继续保存 compatibility base。 FileCacheInputStream 是最外层 Velox SeekableInputStream， 但不重新定义 remote reader 的内部状态合同。

Buffer state

  • internal / working buffer
  • mutable position
  • offset / available
  • hasPendingData / count

Read lifecycle

  • set attach 与 null/zero detach
  • next / eof / cancel
  • 异常后不可重试
  • external mode capability

Position/bounds

  • seek
  • getPosition
  • getFileOffsetOfBufferEnd
  • dynamic right bound

6. Velox 内部实现约束

Pool-backed owned memory

固定 reader/writer buffer 必须通过 MemoryPool 分配，不能使用未计费的 std::vector<char>。

Direct IO alignment

构造时调用 ReadFile::directIo 获取 alignment。owned buffer 满足该 alignment；caller external buffer 不满足时必须拒绝 external mode，不能静默 fallback。

Ownership

底层 ReadFile 使用 shared_ptr；如果保留 raw-pointer 构造，则只允许明确 non-owning 场景并测试 lifetime。

Error propagation

底层 Velox exception 原样传播；compatibility layer 在传播前执行与 CH 相同的 cancel/cleanup 状态转换。

7. Writer compatibility

Writer 与 reader 采用同一策略：公开状态机精确兼容 CH，内部用一个 flattened buffer-state 对象和 Velox primitive 实现。不移植完整通用 WriteBuffer hierarchy，也不把状态机重新设计成 next(data, capacity) + advance。

7.2 zero-copy 的精确定义

当前 remote miss 写 cache

FileCacheInputStream owns BufferPtr B
remote reader writes directly into B
FileSegment::write borrows B
local writer appends string_view(B)
writer detaches B
query keeps B

reader → writer 之间没有 staging memcpy。

后置 Task 016

WriteBufferToFileSegment owns BufferPtr T
producer writes directly into T
FileSegment::write borrows T
local writer appends string_view(T)
writer detaches T

temporary writer → local writer 之间同样没有第二次用户态复制。

这里的 zero-copy 指没有用户态中间 memcpy。调用 WriteFile::append(std::string_view) 时，内核仍会执行正常的 userspace-to-kernel/file IO copy；本设计不要求 splice / sendfile 级 kernel zero-copy。

stateDiagram-v2

  ActiveEmpty --> ActivePending: set(buffer, size, offset > 0)

  ActivePending --> ActiveEmpty: next succeeds

  ActivePending --> Canceled: next throws
settle bytes; cancel; rethrow

  ActivePending --> Finalized: finalize / next / close
  ActiveEmpty --> ActiveEmpty: sync / flush
  ActivePending --> ActiveEmpty: sync / next / flush
  ActiveEmpty --> Canceled: cancel

  Finalized --> Finalized: finalize or cancel are no-op
  Canceled --> Canceled: cancel is no-op

方法精确语义Velox mapping
set(ptr, size, offset) 安装 non-owning working view；position = ptr + offset。set(nullptr, 0, 0) detach。 只改 FileCacheBufferState，不分配、不复制。
next canceled 或 offset 0 时 no-op；否则调用 nextImpl。成功后结算 bytes 并把 position 复位；异常时先结算、cancel，再 rethrow。 nextImpl → WriteFile::append(string_view(workingBegin, offset))；不调用 flush。
sync 先写完 pending bytes，再请求持久化；writer 保持 Active。 next 后调用 WriteFile::flush。
finalize 幂等；canceled 后 finalize 抛异常。失败时 cancel 后传播；成功后 Finalized。 finalizeImpl → next + WriteFile::close。不额外调用 flush，避免把普通 close 变成每段 fsync。
cancel noexcept、幂等；finalized 后 no-op；丢弃 pending bytes，后续 write/finalize 被拒绝。 不调用 append/flush；释放 owned WriteFile，由 local writer 的 non-throwing destructor 关闭 handle。
getFileName 返回底层目标名，供错误和 cleanup 使用。 WriteFile::getName。

7.5 FileSegment lifecycle 与错误处理

完整 segment

setDownloadedUnlocked 先 finalize/close writer；成功后 reset download data、发布 DOWNLOADED，最后校验物理文件大小。

部分 segment，无 continuation

finalize 并 reset writer/reader，释放 handle 和远端状态，再把 segment 缩到实际 downloaded size。

写入失败

cancel 并 reset writer，reset remote reader，设置 download failed 并唤醒等待者；pending bytes 不得再次写入。

background continuation

只有成功进入 download queue 时才保留 writer/reader；后续 downloader 从已有文件尾继续。

WriteFile::append 是同步 all-or-throw 接口，但 local implementation 可能在抛异常前已经发生 partial physical write。异常路径必须读取实际 local file size 并做 reconciliation： 

physicalSize = filesystem::file_size(path)
require downloadedSize <= physicalSize <= reservedSize

if physicalSize == 0:
  remove the empty cache file
else:
  downloadedSize = physicalSize

mark download failed
propagate the original exception with FileSegment diagnostics

这一步只属于 local cache writer；不能依赖通用 WriteFile::size， 因为 short-write exception 前实现可能尚未更新其逻辑 size counter。 CH 可以按 typed errno 只处理 ENOSPC/EDQUOT；Velox WriteFile 当前不暴露 errno，因此这里明确采用“任何 local append exception 都以物理文件大小为准”的 infrastructure adaptation，优先保持 downloaded/reserved/on-disk 三者一致。

7.6 后置 Task 016：WriteBufferToFileSegment

Task 016 不提前实现，但现在固定其兼容边界。它继承同一个 WriteBufferFromFileBase contract，owned memory 是 pool-backed BufferPtr： 

nextImpl:
  acquire downloader
  scope_exit completePartAndResetDownloader
  bytesToWrite = offset
  reserve(bytesToWrite)
  FileSegment::write(ownedBuffer.data, bytesToWrite, writtenBytes)
  writtenBytes += bytesToWrite

finalizeImpl / sync:
  next
  get FileSegment local cache writer
  BufferStateSwapGuard(this, cacheWriter)
  cacheWriter.finalize / cacheWriter.sync

BufferStateSwapGuard 只临时交换 internal/working view 和 position， 不交换两个对象对 BufferPtr / WriteFile 的 ownership； 也不交换各 writer 已结算的 bytes counter。 析构时必须无异常地交换回来。这样 local cache writer 在 detach 状态下也能使用一个 有效的 empty working view 完成 finalize/sync。

8. Task 014 如何使用该合同

FileCacheInputStream owns output BufferPtr B

remote read-and-cache:
  reader.set(B.mutableData, B.capacity)
  reader.next / eof
  FileSegment::write(reader.buffer.begin, reader.buffer.size)
  publish B to Velox caller
  reader.set(nullptr, 0)
  assert reader.available == 0
  assert reader.bufferEndOffset == segment.currentWriteOffset
  release downloader; FileSegment owns reader

outputBuffer_ 就是 CH 外层 reader 的 internal buffer，不是第二个需要复制的 staging buffer。异常路径不得把 canceled reader 放回 FileSegment；必须先释放 downloader/holder，再传播异常。
